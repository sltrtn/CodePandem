## 1. Runtime model: one process, one event loop

When you run the backend:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

`uvicorn` starts a single Python process with a single **event loop** (`backend/main.py` path: `app/main.py`).

- The event loop is **single-threaded**. Every HTTP request, every WebSocket connection, and every background timer is a **task** that yields control at `await`.
- This is why the app can hold thousands of WebSocket connections without threads: as soon as one player is waiting for a match, the loop switches to another player.
- The tradeoff is that **all important state lives in that one process's RAM**. If the process dies, it dies.

State held in memory:

| State | File | Data structure |
|---|---|---|
| Players in queue | `app/matchmaking.py:30` | `dict[str, QueuedPlayer]` (`self._pool`) |
| Live matches | `app/matchmaking.py:31` | `dict[str, Match]` (`self._matches`) |
| Player → match map | `app/matchmaking.py:32` | `dict[str, str]` (`self._player_match`) |
| Parked queue waiters | `app/matchmaking.py:33` | `dict[str, asyncio.Future]` (`self._waiters`) |
| Online lobby | `app/lobby.py` | `dict[str, OnlinePlayer]` (`self._players`) |
| Login rate-limit attempts | `app/auth.py:175` | `dict[str, list[datetime]]` (`_login_attempts`) |

**Why this matters for DevOps:** you cannot start a second backend process and have both serve the same queue. If `replicas: 2`, player A connects to pod 1 and player B connects to pod 2; neither pod knows the other exists, so they never match. The K8s manifest keeps `replicas: 1` for the backend (`k8s/backend.yaml:9`) for exactly this reason.

## 2. Authentication: bcrypt, JWT, and refresh-token rotation

### Password storage

```python
# app/auth.py:27
return bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12)).decode()
```

- Passwords are hashed with **bcrypt** at cost factor 12 (rounds=12). Higher is slower, which is good because it slows brute-force attacks.
- The `password_hash` is stored in `users.password_hash` (`app/models_db.py:25`). Never store a password.

### Access token (short-lived, stateless)

```python
# app/auth.py:55-61
expire = datetime.now(timezone.utc) + expires_delta
return jwt.encode(
    {"sub": user_id, "type": token_type, "exp": expire},
    SECRET_KEY,
    algorithm=ALGORITHM,
)
```

- JWT = JSON Web Token. It is signed with `CODEPANDEM_JWT_SECRET` using HMAC-SHA256 (`HS256`).
- The payload is `{sub: user_id, type: "access", exp: <timestamp>}`.
- Default lifetime: 15 minutes (`app/auth.py:19`).
- It is **stateless**: the server does not store the token anywhere. It only verifies the signature and checks that it has not expired.

### Refresh token (long-lived, revocable)

```python
# app/auth.py:70-80
token_value = secrets.token_urlsafe(32)
expires_at = datetime.now(timezone.utc) + timedelta(days=REFRESH_TOKEN_EXPIRE_DAYS)
rt = RefreshToken(
    token=token_value,
    user_id=user_id,
    expires_at=expires_at,
)
db.add(rt)
db.commit()
return token_value
```

- The refresh token is a random 32-byte string generated by `secrets.token_urlsafe`. It is stored in the database.
- Default lifetime: 7 days (`app/auth.py:20`).
- It is **revocable** because it lives in the DB. Logging out marks it `revoked_at` (`app/auth.py:158-162`).

### Refresh-token rotation

```python
# app/auth.py:133-155
rt.revoked_at = now
new_access = create_access_token(user_id)
new_refresh = create_refresh_token(user_id, db)
db.commit()
return new_access, new_refresh
```

- Every time a client uses a refresh token, the old refresh token is revoked and a **new** one is issued.
- This is called **refresh-token rotation**. If an attacker steals a refresh token, using it once revokes it and the legitimate user is forced to log in again — the theft is detected.

### Protecting routes

```python
# app/auth.py:96-110
user_id = decode_token(cred.credentials, expected_type="access")
if not user_id:
    raise HTTPException(status_code=401, detail="Invalid access token")
user = db.query(User).filter(User.id == user_id).first()
if not user:
    raise HTTPException(status_code=401, detail="User not found")
return user
```

- `get_current_user` is a FastAPI dependency. Any route that needs auth uses `Depends(get_current_user)`.
- It reads the `Authorization: Bearer <token>` header, decodes the JWT, then hits the DB to confirm the user still exists.

### Rate limiting

```python
# app/auth.py:186-207
if len(attempts) >= 5:
    lockout_until = now + timedelta(minutes=15)
    _login_lockouts[identifier] = lockout_until
    return False, int((lockout_until - now).total_seconds())
```

- 5 failed login attempts per identifier per 15 minutes → 15-minute lockout.
- **Important:** this is stored in memory (`dict`), so it only works with a single backend process. If you ever scale horizontally, this rate limiter would break.

### Honest gaps

- Default secret: `CODEPANDEM_JWT_SECRET` defaults to `"codepandem-dev-secret-change-in-prod"` (`app/auth.py:17`). In production this must be a strong random secret, or anyone can forge tokens.
- The DB queries in auth use sync SQLAlchemy. FastAPI runs sync dependencies in a thread pool, so it does not block the event loop, but it is still a thread-per-request cost.

## 3. Matchmaking: futures and event-loop parking

### The queue flow

1. Client opens a WebSocket to `ws://host/ws/queue?token=...` (`app/ws/queue.py:35`).
2. Server validates the token and identifies the user.
3. Client sends `{"type":"join_queue"}`.
4. Server calls `matchmaker.join_queue(...)` (`app/ws/queue.py:94`).

### Inside `join_queue`

```python
# app/matchmaking.py:91-107
loop = asyncio.get_event_loop()
fut: asyncio.Future[str | None] = loop.create_future()
self._waiters[player_id] = fut

self._pool[player_id] = QueuedPlayer(...)

result = await asyncio.wait_for(fut, timeout=CONFIG.MATCHMAKING_MAX_WAIT_S + 2)
```

- An `asyncio.Future` is a placeholder for a result that does not exist yet.
- The coroutine `await`s the future. The event loop **parks** this task and goes to serve other players.
- It will only resume when something else sets the result of this future.

### The matchmaking loop

```python
# app/matchmaking.py:157-163
async def _match_loop(self) -> None:
    while not self._shutdown:
        await asyncio.sleep(CONFIG.MATCHMAKING_SCAN_INTERVAL_S)
        try:
            await self._scan_pool()
        except Exception:
            pass
```

- A background task wakes every 1 second (`MATCHMAKING_SCAN_INTERVAL_S` from `app/config.py:28`) and scans the pool.

### Range widening

```python
# app/matchmaking.py:171-175
new_range = CONFIG.MATCHMAKING_INITIAL_RANGE + (
    (int(elapsed) // CONFIG.MATCHMAKING_WIDEN_INTERVAL_S)
    * CONFIG.MATCHMAKING_RANGE_WIDEN
)
qp.range_size = min(new_range, CONFIG.MATCHMAKING_MAX_RANGE)
```

- Config values: start at 100 ELO points, add 25 every 5 seconds, cap at 400 (`app/config.py:23-27`).
- This means the longer you wait, the wider the ELO gap you can be matched with.

### Matching algorithm

```python
# app/matchmaking.py:194-210
for mode, players in by_mode.items():
    players.sort(key=lambda p: p.elo)
    for i, p1 in enumerate(players):
        if p1.player_id in matched:
            continue
        best = None
        best_diff = float("inf")
        for p2 in players[i + 1 :]:
            if p2.player_id in matched:
                continue
            if p1.ws is p2.ws:
                continue
            diff = abs(p1.elo - p2.elo)
            if diff <= p1.range_size and diff <= p2.range_size:
                if diff < best_diff:
                    best_diff = diff
                    best = p2
```

- Group by mode (`ranked` / `unranked`).
- Sort by ELO.
- Greedy: for each unmatched player, find the closest unmatched player within both players' allowed ranges.
- Time complexity: O(n²) per scan. Fine for small queues, would bottleneck at large scale.

### Waking the parked coroutines

```python
# app/matchmaking.py:214-227
match = self._create_match(...)
if p1.fut and not p1.fut.done():
    p1.fut.set_result(match.match_id)
if best.fut and not best.fut.done():
    best.fut.set_result(match.match_id)
```

- `_create_match` builds the `Match` object with three rounds.
- Then it calls `set_result` on both players' futures.
- That wakes the `await asyncio.wait_for(fut, ...)` in `join_queue`, which returns the `match_id` to the queue WebSocket handler.
- The queue handler then sends `{"type":"match_found"}` to the client.

### Why this is a strong interview talking point

You can draw this on a whiteboard:

- One process → one event loop.
- Background loop scans a pool every second.
- Players are parked on `asyncio.Future` objects.
- Matching sets the future → the event loop resumes the coroutine.

This is the actual async pattern, not just "we use FastAPI."

## 4. Duel lifecycle: submit, judge, score, persist

### Match structure

A match is created with three rounds (`app/config.py:9-11`):

```python
ROUNDS_PER_MATCH: int = 3
ROUND_TIMES: list[int] = [180, 300, 480]        # 3 min, 5 min, 8 min
ROUND_DIFFICULTIES: list[str] = ["easy", "medium", "hard"]
```

### Round timer

```python
# app/ws/duel.py:105-109
async def _start_round_timer(match: Match, rnd: Round) -> None:
    await asyncio.sleep(rnd.time_limit_s)
    if rnd.status != "active":
        return
    await _finish_round(match, rnd)
```

- When the duel starts, the server schedules a background task that sleeps for the round time, then calls `_finish_round`.
- The guard `if rnd.status != "active"` prevents double-finishing if both players submitted just before the timer fired.

### Submit path

```python
# app/ws/duel.py:342-416
if msg_type == "submit":
    code = data.get("code", "")
    telemetry_raw = data.get("telemetry", {})
    telemetry = Telemetry(...)
    rnd = match.rounds[match.current_round - 1]
    result = await run_submission(code, rnd.problem)
    cheat = calculate_cheat_score(telemetry, rnd.problem, code)
    result.cheat_score = cheat.composite
    result.suspicious = cheat.suspicious
    time_limit_ms = rnd.time_limit_s * 1000
    round_score = score_submission(result, time_limit_ms)
    prs.score += round_score
    prs.submissions += 1
    prs.last_result = result
    await _broadcast(match, {...})
```

Steps:
1. Receive the submitted code and telemetry from the frontend.
2. Build a `Telemetry` dataclass.
3. Run the code against the problem's test cases.
4. Calculate anti-cheat score.
5. Score the submission.
6. Update the player's round state.
7. Broadcast the new state to both players (and spectators).

### Judge call

```python
# app/judge.py:12-14
JUDGE_MODE = os.getenv("JUDGE_MODE", "process")
JUDGE_URL = os.getenv("JUDGE_URL", "http://judge:9000")

# app/judge.py:42-45
async def run_submission(code: str, problem: Problem) -> SubmissionResult:
    if JUDGE_MODE == "http":
        return await _judge_http(code, problem)
    return await judge_code(code, problem)
```

- In Docker and K8s, `JUDGE_MODE=http` and `JUDGE_URL=http://judge:9000`.
- The backend sends the code and test cases to the judge service over HTTP.
- The judge service is a separate container because it runs untrusted code.

### Anti-cheat scoring

```python
# app/anticheat.py:128-148
composite = round(
    speed * 0.20
    + paste * 0.25
    + tabs * 0.15
    + keys * 0.10
    + pattern * 0.15
    + plagiarism * 0.15,
    4,
)
```

| Signal | What it catches | Weight |
|---|---|---|
| speed | Solved faster than humanly possible | 20% |
| paste | Zero keystrokes but long code | 25% |
| tabs | Too much time alt-tabbed | 15% |
| keystrokes | >15 keys/sec or <0.5/sec with 100+ chars | 10% |
| typing_pattern | Near-zero variance in keystroke intervals | 15% |
| plagiarism | Repeated lines or answer hidden in code | 15% |

`composite > 0.3` is suspicious, `> 0.5` is flagged (`app/config.py:20-21`).

### Submission scoring

```python
# app/scoring.py:6-16
if result.test_cases_total == 0:
    return 0.0
base = result.test_cases_passed / result.test_cases_total
speed = max(0.0, 1.0 - (result.time_ms / time_limit_ms))
return round(base + (speed * 0.01), 6)
```

- Correctness is almost everything. Speed is a tiny tiebreaker (max 1% bonus).
- The winner is whoever has the higher cumulative score across the round.

### Round and match finish

```python
# app/ws/duel.py:112-176
async def _finish_round(match: Match, rnd: Round) -> None:
    rnd.status = "finished"
    winner_id = determine_round_winner(rnd)
    rnd.winner = winner_id
    if winner_id:
        match.players[winner_id].round_wins += 1
    # ... broadcast round_over ...
    # First to 2 wins → match_over
    for ps in match.players.values():
        if ps.round_wins >= CONFIG.WINS_NEEDED:
            match.winner = ps.player_id
            match.status = "match_over"
            # broadcast match_over
            matchmaker.remove_match(match.match_id)
            _persist_match(match)
            return
```

- `WINS_NEEDED = 2` (`app/config.py:13`). Best of 3 rounds.
- At match end, the match is removed from memory and `_persist_match` writes it to the database.

### ELO persistence

```python
# app/ws/duel.py:265-287
K = 32
expected = 1 / (1 + 10 ** ((opponent.elo - player.elo) / 400))
if match.winner == player_id:
    score = 1.0
elif match.winner:
    score = 0.0
else:
    score = 0.5
return round(K * (score - expected), 1)
```

- Standard Elo formula with K=32.
- Winner gets `+K * (1 - expected)`, loser gets `+K * (0 - expected)`.
- The change is stored in `MatchRecord.player1_elo_change` / `player2_elo_change` and added to the user's `elo` field.
- Season stats are also updated (`UserSeasonStats` table).

### Honest gap

`_persist_match` (`app/ws/duel.py:178-262`) and `_calc_elo_change` (`app/ws/duel.py:265-289`) do synchronous DB queries inside the async WebSocket handler. This blocks the event loop while SQLite writes. At scale, persistence should be pushed to a separate worker or async SQLAlchemy should be used.

## 5. Judge: running untrusted code

### Two modes

```python
# app/judge.py:12-14
JUDGE_MODE = os.getenv("JUDGE_MODE", "process")  # default: run in-process
JUDGE_URL = os.getenv("JUDGE_URL", "http://judge:9000")
```

- `process`: the backend itself runs the code. Only for local development.
- `http`: the backend sends code to the judge worker container.

### Judge worker

```python
# app/judge_worker.py:14-15
CONCURRENCY = int(os.getenv("JUDGE_CONCURRENCY", "4"))
_semaphore = asyncio.Semaphore(CONCURRENCY)

# app/judge_worker.py:38-51
@app.post("/judge")
async def judge(req: JudgeRequest) -> dict:
    problem = Problem(test_cases=req.test_cases)
    async with _semaphore:
        result: SubmissionResult = await judge_code(req.code, problem)
    return {...}
```

- The judge worker is a FastAPI service on port 9000.
- A semaphore caps concurrent executions at 4. This prevents one burst of submissions from consuming all CPU/memory.

### The wrapper

```python
# app/executor.py:23-50
def _build_wrapper(code_file: str, mem_bytes: int) -> str:
    return textwrap.dedent(f"""\
        import sys, resource, io
        try:
            resource.setrlimit(resource.RLIMIT_AS, ({mem_bytes}, {mem_bytes}))
        except ValueError:
            pass
        with open({repr(code_file)}, 'r') as _f:
            _user_code = _f.read()
        _old_stdout = sys.stdout
        sys.stdout = _buf = io.StringIO()
        try:
            exec(compile(_user_code, '<user>', 'exec'))
        except SystemExit:
            pass
        except Exception as e:
            sys.stdout = _old_stdout
            print(f'ERROR: {{e}}', file=sys.stderr)
            sys.exit(1)
        _output = _buf.getvalue().rstrip('\\n')
        sys.stdout = _old_stdout
        print(_output)
    """)
```

- The wrapper:
  1. Sets `RLIMIT_AS` (address-space limit) to 128 MB.
  2. Reads the user's code from disk.
  3. Redirects stdout to a buffer.
  4. `exec(compile(user_code, '<user>', 'exec'))` actually runs the code.
  5. Prints the captured output.

### Subprocess execution

```python
# app/executor.py:72-83
proc = await asyncio.create_subprocess_exec(
    "python3", "-c", wrapper_code,
    stdin=asyncio.subprocess.PIPE,
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
)
stdout_bytes, stderr_bytes = await asyncio.wait_for(
    proc.communicate(input=test_input.encode()),
    timeout=timeout_s,
)
```

- The wrapper is spawned as a **subprocess**.
- Test input is piped to stdin.
- `asyncio.wait_for` enforces the time limit (5 seconds). If it times out, the result is "Time Limit Exceeded".
- Return code 0 + stdout matching expected output = test passed.

### Soft sandbox, not hard sandbox

This is a **soft sandbox**:
- Memory cap: `RLIMIT_AS`.
- Time cap: `asyncio.wait_for`.
- User cap: runs as non-root `judge` user in its own container.
- Filesystem cap: `readOnlyRootFilesystem` in K8s.

It is **not** a hard sandbox. A determined user could still use network or filesystem calls. A real production sandbox would use **gVisor**, **Firecracker**, or **nsjail/seccomp**.

### Why the emptyDir volume matters

```yaml
# k8s/judge.yaml:23-56
volumes:
  - name: tmp
    emptyDir: {}
containers:
  - name: judge
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop:
          - ALL
    volumeMounts:
      - name: tmp
        mountPath: /tmp
```

- `readOnlyRootFilesystem: true` makes the entire container filesystem read-only.
- The judge still needs to write temp files to `/tmp`, so an `emptyDir` volume is mounted at `/tmp`. This is the only writable space.
- Without this, the judge fails because `executor.py` writes to `/tmp` (`app/executor.py:64`). This is a real bug you hit and fixed.

## 6. Docker: packaging and wiring

### Backend Dockerfile

```dockerfile
# backend/Dockerfile
FROM python:3.14-slim
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
ENV CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173,http://localhost
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

- `python:3.14-slim` — Debian-based Python image, stripped of extra packages.
- `PYTHONDONTWRITEBYTECODE=1` — prevents `.pyc` files, keeps image small.
- `PYTHONUNBUFFERED=1` — logs flush immediately so `docker logs` works.
- `COPY requirements.txt .` happens **before** `COPY . .`. This is deliberate for **layer caching**: Docker caches the `pip install` layer unless `requirements.txt` changes. Code changes only invalidate the later `COPY . .` layer.
- `EXPOSE 8000` is metadata only; it does not open the port.
- `CMD` is the default command. It can be overridden at runtime.

### Judge Dockerfile

```dockerfile
# backend/Dockerfile.judge
RUN useradd -m judge
RUN chown -R judge:judge /tmp
USER judge
EXPOSE 9000
CMD ["uvicorn", "app.judge_worker:app", "--host", "0.0.0.0", "--port", "9000"]
```

- Creates a non-root user.
- Switches to that user before running the server.
- This is the first security layer: if submitted code escapes, it is running as `judge`, not `root`.

### Docker Compose

```yaml
# docker-compose.yml
services:
  backend:
    build:
      context: ./backend
    ports:
      - "${BACKEND_PORT:-8000}:8000"
    volumes:
      - codepandem_db:/app/data
    environment:
      - DATABASE_URL=sqlite:///./data/codepandem.db
      - CORS_ORIGINS=...
      - JUDGE_MODE=http
      - JUDGE_URL=http://judge:9000
    depends_on:
      judge:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "python", "-c", "urllib.request.urlopen('http://localhost:8000/health')"]
```

- **Named volume** `codepandem_db` mounted at `/app/data` is what makes SQLite survive container restarts.
- **Service discovery**: the backend calls `http://judge:9000`. Docker Compose creates an internal DNS entry `judge` that resolves to the judge container.
- **Ordering**: `depends_on: condition: service_healthy` means the backend waits until the judge healthcheck passes before starting.
- **Healthcheck**: the backend polls `http://localhost:8000/health`. The `start_period` gives the app 5 seconds before failures count.
- **Env defaults**: `${BACKEND_PORT:-8000}` means "use the env var, or 8000 if unset."

### Frontend nginx

```nginx
# frontend/nginx.conf
location /api/ {
    proxy_pass http://backend:8000/;
}
location /ws/ {
    proxy_pass http://backend:8000/ws/;

```

- The frontend container is nginx. It serves the React build and proxies `/api/` and `/ws/` to the backend container.
- The `Upgrade` and `Connection` headers are required for WebSocket proxying.

## 7. Kubernetes: declaring desired state

### Kubernetes mental model

Kubernetes is not a script. You write YAML files that describe **what you want to be true**. Controllers constantly watch reality and fix it. This is the declarative model.

### Namespace

```yaml
# k8s/namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: codepandem
```

- A namespace is a bucket that isolates this app's resources from other apps on the same cluster.

### ConfigMap

```yaml
# k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: codepandem-config
  namespace: codepandem
data:
  JUDGE_MODE: "http"
  JUDGE_URL: "http://judge:9000"
  CORS_ORIGINS: "http://codepandem.local:8080,..."
```

- ConfigMap holds non-secret configuration.
- `envFrom.configMapRef` injects these as environment variables into every pod.

### Deployment

```yaml
# k8s/backend.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: codepandem
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: backend
          image: ghcr.io/sltrtn/codepandem/backend:latest
          imagePullPolicy: Always
          ports:
            - containerPort: 8000
              name: http
          envFrom:
            - configMapRef:
                name: codepandem-config
          readinessProbe:
            httpGet:
              path: /health
              port: http
          livenessProbe:
            httpGet:
              path: /health
              port: http
          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "512Mi"
              cpu: "500m"
```

- `replicas: 1` — only one pod. Because of in-memory state, you cannot increase this without redesigning the app.
- `selector` / `matchLabels` — the Deployment owns pods with `app: backend`. The Service uses the same label to send traffic to them.
- `imagePullPolicy: Always` — pull the latest image on every pod creation.
- `envFrom.configMapRef` — injects the ConfigMap.
- **Readiness probe** — the pod is only added to the Service's endpoints after `/health` succeeds.
- **Liveness probe** — if `/health` fails repeatedly, kubelet kills the container and starts a new one. This is self-healing.
- **Resources**:
  - `requests` — the scheduler uses this to pick a node with enough capacity. `100m` CPU = 0.1 core.
  - `limits` — the hard ceiling. The pod is throttled at 500m CPU and OOM-killed at 512Mi memory.

### Service

```yaml
# k8s/backend.yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: codepandem
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
    - port: 8000
      targetPort: http
      name: http
```

- `ClusterIP` — only reachable inside the cluster.
- `selector: app: backend` — traffic goes to pods with that label.
- `targetPort: http` — the named port in the pod spec. Named ports are useful when you want to keep port numbers in one place.
- Inside the cluster, other pods can reach the backend at `http://backend:8000`.

### Judge Deployment

```yaml
# k8s/judge.yaml
spec:
  replicas: 2
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
  containers:
    - name: judge
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
      volumeMounts:
        - name: tmp
          mountPath: /tmp
```

- `runAsNonRoot: true` — the pod will not start if the image tries to run as root.
- `runAsUser: 1000` — matches the `judge` user created in `Dockerfile.judge`.
- `readOnlyRootFilesystem: true` — the container's root filesystem is read-only.
- `allowPrivilegeEscalation: false` — prevents `setuid` binaries from becoming root.
- `capabilities: drop: - ALL` — removes all Linux capabilities.
- `emptyDir` mounted at `/tmp` — the only writable path.
- `replicas: 2` — the judge is **stateless**, so it can scale. The backend calls `http://judge:9000` and the Service load-balances across the two pods.

### Ingress

```yaml
# k8s/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: codepandem
  namespace: codepandem
spec:
  rules:
    - host: codepandem.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
```

- The Ingress is the cluster's front door.
- `host: codepandem.local` — requests with that Host header hit this rule.
- `path: /` → forwarded to the `frontend` Service on port 80.
- nginx inside the frontend pod then proxies `/api/` and `/ws/` to the backend.
- k3d exposes the Ingress on port 8080 via `--port 8080:80@loadbalancer` from cluster creation.

### Full request path in the cluster

```
Browser (codepandem.local:8080)
  → Ingress (Traefik)
    → frontend Service
      → frontend Pod (nginx)
        → /api/ or /ws/ → backend Service
          → backend Pod
            → /judge → judge Service
              → judge Pod
                → subprocess
```

## 8. What the architecture makes easy and hard

### Easy

- Single codebase, single mental model.
- FastAPI + asyncio = high concurrency on one process.
- Docker / Compose / K8s are all simple because there are only three services.
- CI/CD pipeline is small: lint, 35 tests, frontend build, GHCR push.

### Hard

- **Horizontal scaling**: you cannot add backend pods without Redis or a shared matchmaking service.
- **Database persistence in K8s**: the K8s backend manifest has no volume. The SQLite database lives inside the container. If the pod is rescheduled, the database is gone. Docker Compose solved this with a named volume; K8s does not currently.
- **Blocking DB calls**: sync SQLAlchemy queries inside WebSocket handlers block the event loop briefly.
- **Soft sandbox**: the judge is not a real isolation boundary.
- **Rate limiting**: in-memory only.

### Production path (if you ever take it there)

1. Add a persistent volume to the K8s backend, or move to PostgreSQL.
2. Move matchmaking state to Redis or a separate matchmaking service.
3. Make the judge async-safe or use an external sandboxed runner (gVisor/Firecracker).
4. Use async SQLAlchemy or a worker queue for persistence.
5. Add Redis for rate limiting and WebSocket coordination across backend replicas.

## 9. Why this matters in an interview

You can say something like this:

> "The backend is a single-process FastAPI app with an asyncio event loop. It holds live state in memory — the queue, the matches, the lobby — so it must run as exactly one replica. Authentication uses bcrypt for passwords, short-lived JWT access tokens, and revocable refresh tokens with rotation. Matchmaking parks players on `asyncio.Future` objects and a background loop scans the pool every second, widening the ELO range over time until it finds a match. The duel flow sends submitted code to a separate judge container, which executes it in a subprocess with a memory limit and timeout, then scores correctness and runs anti-cheat heuristics. The whole stack is containerized with Docker, wired with Docker Compose using healthchecks and startup ordering, and deployed to a local k3d cluster with Kubernetes Deployments, Services, an Ingress, readiness/liveness probes, and a non-root, read-only judge pod."

## 10. Common traps

**"Can you just scale the backend to 5 replicas?"**

No. Matchmaking state is in a Python dict in one process. Five replicas = five isolated queues. You would need Redis or a shared matchmaking service.

**"Is the judge a real sandbox?"**

No. It is a soft sandbox: memory limit, timeout, non-root user, read-only filesystem. A real sandbox would use gVisor, Firecracker, or nsjail.

**"Why is the backend `replicas: 1` in K8s?"**

Because of in-memory state. The replicas field is not a mistake; it is an intentional constraint of the current design.

**"What happens if the backend pod restarts?"**

Live matches and queued players are lost. In Docker Compose, the SQLite file survives because of the named volume. In K8s as written, the SQLite file is lost because the backend pod has no persistent volume.

**"Why does the judge pod need an `emptyDir` at `/tmp`?"**

Because `readOnlyRootFilesystem: true` makes the whole container read-only, but the judge still writes temporary files to `/tmp` during code execution. The `emptyDir` volume is the only writable space.

**"What does `100m` CPU mean?"**

`100m` = 100 millicores = 0.1 CPU cores. It is a request, not a hard limit; the limit is `500m`.

**"Why does the frontend call `/api/...` and `/ws/...` instead of the full backend URL?"**

Because in dev the Vite proxy forwards `/api` and `/ws` to `localhost:8000`, and in production nginx in the frontend container forwards them to the backend. This works for same-origin deployment but breaks on Vercel, which is why a split deployment needs code changes.
