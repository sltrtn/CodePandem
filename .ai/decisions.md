# CodePandem — Architectural Decisions

> Every important decision with date, reason, alternatives, and consequences.

---

## 2026-07-26 — FastAPI + WebSocket (No REST for Real-time)

**Decision:** Use WebSocket for all real-time flows (matchmaking, duel), REST only for health checks and static problem listing.

**Reason:** The duel flow requires sub-second message delivery — REST polling would add latency and complexity. WebSocket provides a single persistent connection for bidirectional communication.

**Alternatives Considered:**
- Server-Sent Events (SSE) — unidirectional, would need separate POST for submissions.
- REST polling — wasteful, latency, requires client-side polling logic.
- gRPC streaming — heavier dependency, overkill for 2-player duels.

**Consequences:**
- All game state transitions happen via WebSocket messages.
- Client must handle WebSocket lifecycle (reconnection, error states).
- Server must manage concurrent WebSocket connections per match.

## 2026-07-26 — Tiered Scoring (Test Cases > Speed)

**Decision:** Test cases are the primary ranking factor. Speed is tiebreaker only.

**Reason:** A solution that passes 5/5 test cases is always better than 3/5 regardless of speed. Speed as tiebreaker prevents ties without distorting the scoring hierarchy.

**Alternatives Considered:**
- Weighted score (speed * accuracy) — allows fast-wrong to beat slow-correct, which is wrong.
- Pure correctness — too many ties, no tiebreaker.
- Time penalty (like competitive programming) — good but less dramatic for 1v1.

**Consequences:**
- `score_submission()` returns 0.0-0.8 based on test cases, +0.0-0.2 bonus for speed.
- Mathematically impossible for speed to overcome a test case difference.
- Clear ranking: correctness always wins.

## 2026-07-26 — Subprocess Judge (No Docker)

**Decision:** Execute user code in a subprocess with `resource.setrlimit` for memory and `asyncio.create_subprocess_exec` for timeout.

**Reason:** For a local M1 platform, Docker is overkill. Subprocess with resource limits provides adequate isolation for a learning/portfolio project.

**Alternatives Considered:**
- Docker containers — stronger isolation but heavier, slower cold start.
- Restricted Python exec — `exec()` in same process, risk of resource exhaustion.
- Online judge API (HackerRank, Judge0) — external dependency, rate limits.

**Consequences:**
- User code runs in the same Python process's children.
- Memory capped at 128MB via `resource.setrlimit`.
- Timeout at 5s via `asyncio.wait_for`.
- `sys.exit()` in user code raises `SystemExit` (BaseException), must be caught separately.
- No network access from user code (no sandbox, just resource limits).

## 2026-07-26 — In-Memory State → SQLite Database

**Decision (M1):** All match state lives in memory. No database, no persistence.
**Updated (M3):** Added SQLite + SQLAlchemy for user accounts, match history, and ELO persistence.

**Reason:** M1 was a local prototype. M3 added profiles and leaderboards which require persistence. SQLite is the simplest option — zero config, single file, no server.

**Consequences:**
- User accounts persist across restarts.
- Match history and ELO changes are recorded.
- Server restart still loses active matches (in-memory), but completed matches are saved.
- Future: migrate to PostgreSQL for production deployment.

## 2026-07-26 — Client-Generated Player IDs → Server-Assigned IDs

**Decision (M1):** Player IDs are generated by the frontend and sent with join_queue.
**Updated (M3):** Player IDs are now server-assigned user IDs from the database (12-char hex). JWT auth validates identity.

**Reason:** Authentication requires server-assigned IDs. JWT tokens carry the user_id, which is validated on every WebSocket connection and REST request.

**Consequences:**
- Player IDs are stable across sessions (tied to account).
- Identity is cryptographically verified via JWT.
- Matchmaker uses server-validated user_id as the key.
- Frontend stores both token and playerId in localStorage.

## 2026-07-26 — Dark Theme Only

**Decision:** Ship only a dark theme. No light mode toggle.

**Reason:** Competitive coding platforms are overwhelmingly dark-themed (LeetCode, Codeforces, HackerRank). Dark reduces eye strain for extended coding sessions. One theme means less CSS and no toggle logic.

**Alternatives Considered:**
- Light + dark with toggle — more work, more CSS, more context.
- System preference detection — adds complexity with no user demand.

**Consequences:**
- `app.css` uses dark backgrounds (#0a0a0f, #111827, #1e293b) with light text.
- No CSS variables for theming — hardcoded dark values throughout.
- Future: add light mode only if users request it.

## 2026-07-26 — React with Plain Textarea (No Monaco)

**Decision:** Use a plain `<textarea>` for code input, not Monaco Editor.

**Reason:** Monaco is 5MB+ and overkill for a 1v1 battle platform where speed of load matters more than IDE features. A textarea with anti-cheat telemetry is sufficient for the core experience.

**Alternatives Considered:**
- Monaco Editor — full IDE experience but heavy, slow to load, complex to configure.
- CodeMirror — lighter than Monaco but still adds significant bundle size.
- Ace Editor — middle ground but still unnecessary for a battle platform.

**Consequences:**
- Zero syntax highlighting or autocompletion.
- Much faster page load and smaller bundle.
- Anti-cheat telemetry (paste, keystrokes) is simpler to implement on a textarea.
- Future: add syntax highlighting with a lightweight library if needed.
